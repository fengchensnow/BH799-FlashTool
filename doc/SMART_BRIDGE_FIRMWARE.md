# SMART 记录与「中间固件」清 0

## 结论先说

**唯一必须记住的规则：清除用的中间固件，必须与最终刷回的固件 `0xCD` 同源（同为块 1 或同为块 3）。**

`0xCD` bit0 决定 SMART 记录落在 eMMC 保留区的哪一块，而且这个字节在固件里被 **12 处**代码读取，不止开机初始化那一次。只改其中一处、让写地址与最终固件的读地址对不上，写入就会失败。这是过往多轮试错后确认的硬约束。

三步流程（顺序不可省）：

```
1. 刷入与最终固件同源的中间固件
2. 完整断电 → 再上电一次      ← 全 0 记录在此步写入，不能省
3. 断电 → 刷回最终固件 → 上电：SMART 从 0 正常累计
```

## SMART 记录在哪、长什么样

| 项 | 结论 |
|---|---|
| 位置 | eMMC **保留区一个 512 B 块**，不在 SPI Flash；整片刷固件不会动它 |
| 选择 | `fw_param+0xCD` bit0：`0` → 块 1（BLOCK2），`1` → 块 3（BLOCK4）；被 12 处代码读取 |
| 地址 | 运行期保留区基址 `+ addr_offset`（1 或 3），按实测容量算出 |
| 格式 | 14 个 64 位计数器以成对 32 位 word 散布在固定偏移；**无 magic、无版本、无 CRC** |
| 合法性 | 唯一判断是首 dword `== 0xFFFFFFFF` 才清零（初始行为，不是命令）；其余任意字节都会被直接接受 |
| 回写 | 1h timer / 关机 / FW Commit 前由 `smart_info_writeback` 落盘 |

因此 GD→XM 升级后的经典异常是：GD 把 namespace / 配置结构写在块 1，XM 默认读块 1，把别人的数据当 SMART 记录解析（元数据被拼进 64 位计数器高 32 位）→ 出现「写入量 ≈ 容量」「Host Write = `0x80000000xx`」这类 2³² 量级值，且 1h 回写把垃圾固化。记录格式跨版本是兼容的，问题在**读到了别人的数据且没有任何校验**。

固件本身**没有清 0 能力**：NVMe 1.4 无 clear-SMART 命令；LID `0x02` 只读；厂商 LID `0xC0` 只 memcpy 1KB 头；`0x80` Format NVM 只擦命名空间 LBA，够不到保留区；对 SMART 结构体的所有写都是累加。只改 RAM 会被回写覆盖。

`Percentage Used`、温度、Available Spare 由 eMMC EXT_CSD / 运行期计数重新计算，**不在 512 B 记录里**，清块对它们无效。

## 中间固件做了什么

中间固件 = 「最终那份 XM 镜像 + 3 条指令」，header（`0xCD`、卡配置、`0x38`、SN、型号、段表）逐字节不变，不扩镜像，只重算 DWORD31 XOR：

| 改动 | 作用 |
|---|---|
| `smart_info_init` 的 `rw_opt`：READ(1) → WRITE(0) | 开机把全 0 缓冲区**写**进保留块，而不是读 |
| `smart_info_writeback` 入口改 `retl` + 延迟槽 `nop` | 所有落盘入口变 no-op，运行痕迹不会被写回 |
| DWORD31 XOR 重算 | body 变了，校验必须跟上 |

因为 `smart_rw` / `temp_buffer` / `smart_data` 的 `.data` 初值全 0，写出的就是完整 512 B 全 0 合法记录；首 dword 为 0 不会触发固件的自动清零，但数据本身已是 0，结果等价，且不会触发回写覆盖。路径 B（`0xCD=1`）底包天然选 `addr_offset=3`，**无需再改地址**。

## 两条路径与当前产物

| | 最终固件 | 最终读块 | 中间固件 | 状态 |
|---|---|---|---|---|
| 路径 A | `XM25QH80B@SOIC8.BIN`（`0xCD=0`） | 块 1 | `XM25QH80B_blk1_bridge.bin` | 用户真机验证有效 |
| 路径 B | `0xCD=1` 的最终固件 | 块 3 | `XM25QH80B_blk3_bridge.bin` | 用户真机验证有效 |

两个 bridge 文件都预置在两个工具目录的 `FIRMWARE/` 下，工具菜单 3 直接校验 SHA-256 后使用，**不现场生成补丁**。它们各自相对自己的底包只改 header 的 DWORD31 与 body 的 3 个 word（合计 4 个 u32），SPI 配置字、SN、型号、`0xCD`、段表、body 长度全部原样保留。

> 命名说明：`blk3` / `块 3` / `BLOCK4` / `0xCD=1` 指同一件事。菜单 3 里按「blk1 / blk3」选择，对应 `0xCD=0` / `0xCD=1`。

**不要混用**：路径 A 的最终固件不要换成 `0xCD=1` 的版本，路径 B 的中间固件不要换成 blk1 的那个。

## 与其它方案的区别

| | 改 `0xCD` 绕到空块 | 中间固件清 0 | 上报恒 0 |
|---|---|---|---|
| 改什么 | header 一个字节 | body 3 条指令 + XOR | body 跳过构造 |
| 原理 | 换块读 | 把当前块本身清成全 0 | 只改显示 |
| 历史是否被清 | 否 | **是** | 否 |
| 之后是否累计 | 正常 | 正常 | 不累计 |
| 前提 | 目标块当前为空 | 必须同源 + 完整断电 | — |

`-smart-block` 式的绕块做法只在目标块为空时有效；若该块已被写脏，绕过去**不会清掉历史**，这时必须用中间固件。

## 刷写注意

- 若刷回最终固件后旧 SMART 又出现，优先检查这一步是否走了在线 `FW Commit`——该路径会把 SMART 结构体写回同一块；改用编程器整片刷。
- 用 NVMe FW Download/Commit 刷中间固件时，commit 后同样需要复位。
- **静态校验通过 ≠ 真机可用**：过往失败版本里字节码、XOR 校验、反汇编全部正确，但运行时写入没有发生。缺少运行时观测手段时，不要靠连续盲改 + 烧录去猜结果。
- 刷写前备份 1KB 头（工具菜单 2）；清块会覆盖该保留块原有内容；中途失败 / 掉电会变砖，只能用 SPI 编程器恢复。
