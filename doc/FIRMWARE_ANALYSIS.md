# BH799BB 固件镜像结构与两版差异

分析对象为两个工具目录 `FIRMWARE/` 下的 4 个文件（两版内容一致）。结论均已按字节复核，并以当前实际文件名为准。

| 文件 | 大小 | SHA-256 | 角色 |
|---|---|---|---|
| `GD25Q80@USON8.bin` | 1,048,576 B (`0x100000`) | `6723ead9…4ad1abdd` | GD 底包，整机客户版 |
| `XM25QH80B@SOIC8.BIN` | 1,048,656 B (`0x100050`) | `a3940e3a…8cf6b4` | XM 底包，工程版（含 80 B 编程器尾） |
| `XM25QH80B_blk1_bridge.bin` | 1,048,656 B | `bc6a3098…4adecfd0` | 中间固件，`0xCD=0` |
| `XM25QH80B_blk3_bridge.bin` | 1,048,576 B | `e998c426…3b9b1f1d` | 中间固件，`0xCD=1` |

两片 SPI NOR 都是 8 Mbit（1 MB）。XM 底包多出的 80 B 是 `-Configuration-` 编程器配置尾，**不是固件内容**，刷写与计算校验前必须裁掉。

## 镜像格式与校验

```
文件 0x000 – 0x3FF : 1 KB 头 = 256 个大端 u32（引导头 + 客户参数区）
文件 0x400 – …     : body（陷阱/向量表、.text、.rodata、.data），加载到 VA 0x40000000
```

地址换算：`VA = 0x40000000 + (file_offset - 0x400)`，反向为 `file_offset = VA - 0x40000000 + 0x400`。注意 body 从文件 `0x400` 起才映射到 `0x40000000`，直接用 `file_offset` 相加会整体偏大 `0x400`。

两项校验（4 个文件实测全部通过）：

- **DWORD0**（文件 `0x00`）：四个字节异或 `b0^b1^b2^b3 == 0xFF`（奇偶），低 24 位 = body 长度。XM `0xD2020F20` → 长度 `0x20F20`；GD `0xE2020718` → `0x20718`。
- **DWORD31**（文件 `0x7C`）：`0x400..0x100000` 范围内大端 u32 的 XOR，文件中以小端存放。XM 计算值 `0xCA11DA1B`、GD `0x935F09D4`，与写入值一致。范围上限是 1 MB，**不含 80 B 尾**。

> 客户参数区 `0x000–0x3FF` 不在上述两项校验范围内。改 SN / 型号 / 掩码 / `0xCD` / `0x105` 等字段**无需重算校验**；改动 body 才需要重算 DWORD31。

### 段表（头 DWORD1–6）

| 段 | XM | GD |
|---|---|---|
| .text VA / 大小 | `0x40000000` / `0x1EE18` | `0x40000000` / `0x1A908` |
| .data VA / 大小 | `0x4001EE18` / `0x2108` | `0x4001A908` / `0x5E10` |
| .bss VA / 大小 | `0x40020F20` / `0x9C5` | `0x40020718` / `0x28C8` |

GD 代码少约 17.7 KB，但 .data 多约 15.6 KB、.bss 多约 7.9 KB。段表必须与所选底包保持一致，跨底包拼装时不能照搬。

## 两版关键差异

| 偏移 | XM | GD | 说明 |
|---|---|---|---|
| `0x038` (dw14) | `0x800010D8` | `0x00000000` | **SPI Flash 配置字**，与板上 SPI 芯片型号绑定；跨板型刷写前必须核对 |
| `0x080`–`0x0CF` | 多项非零 | 多数为 0 | 客户位域，XM 是 GD 的超集 |
| `0x0C9` bit6 | 置位 | 清零 | 诊断命令 / SMART 更新开关 |
| `0x0CD` bit0 | 0 / 1 | 0 | SMART 记录块选择，见 `SMART_BRIDGE_FIRMWARE.md` |
| `0x105` bits7:6 | `0x80` (LED) | `0x40` (UART) | GPIO0 模式，见 `gpio0_uart_led_mode.md` |
| `0x10C` SN | `29036200000000000001` | `NA6169D003A74` | 20 B |
| `0x120` Model | 全 0 → 动态拼装 | `E2M2 64GB` → 静态 | 40 B |
| `0x148` 掩码 | `0xBC` | `0xBD` | 拼装位掩码，**首字节有效** |
| `0x14C` OEM | `OEM` | `OEM` | 8 B |
| `0x154` 覆盖串 | 空 | 空 | 8 B |
| 版本串（.data） | `10100140` | `10100080` | 8 B，NVMe Identify 的 FR |

- **GD = 量产客户版**：型号硬编码，SMART 采集被裁（`smart_info_update_by_ops` 无调用者，计数器恒 0），带 Format NVM / Secure Erase、HS400 相位调优，调试打印被裁。
- **XM = 工程调试版**：型号运行时动态拼装，SMART 采集完整（6 处累加调用点），带错误重试统计与降级日志。
- 两者 Get Log Page 都支持 LID `1/2/3/5/0xC0`；XM 也实现了 `0x80` Format NVM（它只擦命名空间 LBA，够不到 eMMC 保留块里的 SMART 记录）。

## 客户参数区真值表

以 `FIRMWARE/` 实测为准。以下偏移由固件运行期直接读取（1KB 头原样拷到 RAM `0x40027C00`）：

| 偏移 | 长度 | 字段 | 备注 |
|---|---|---|---|
| `0x10C` | 20 B | SN | Identify 字节 4–23 |
| `0x120` | 40 B | Model | 首 dword ≠ 0 时原样使用，= 0 时动态拼装 |
| `0x144` | 4 B | **全 0，不是字段** | 掩码在 `0x148`，别混 |
| `0x148` | 1 B | 拼装掩码 | `0xBC`/`0xBD`；后 3 字节为 0 |
| `0x14C` | 8 B | OEM 串 | 由掩码 `0x40` 位控制 |
| `0x154` | 8 B | MID 厂商名覆盖串 | 写入值须自带 `-`；`0x15C` 是在用字段，不可越界 |
| `0x0CD` | 1 B | SMART 块选择 bit0 | 被 12 处代码读取 |
| `0x105` / `0x107` | 1 B | GPIO0 模式 / 电平 | 见专文 |
| `0x3E0–0x3FF` | 32 B | 产线工具记录 | 固件不读，拼装时保留底包该区 |

**掩码位名**（以反汇编为准）：`0x80=VEN`、`0x40=OEM`、`0x20=MID`、`0x10=PNM`、`0x08=FWVER`、`0x04=CAP`、`0x01=DISK`，`0x02` 未使用。这四位顺序容易记反；掩码值以 `0x148` 实际字节为准（XM `0xBC`、GD `0xBD`）。详见 `model_name_dynamic_assembly.md`。

头里**没有**容量、温度、Available Spare、Percentage Used 字段：这些来自 eMMC CSD/EXT_CSD 与运行期计数，只能改代码或改卡。

## 在线升级路径

固件本身支持用 NVMe Admin 命令把镜像写进 SPI Flash，无需编程器（编程器仍是失败后的兜底）：

- `Get Log Page` LID `0xC0` 把 RAM 中的 1KB 头 memcpy 到 DMA 缓冲，可读回做校验（开机时拷贝，刷完需复位再读）。USB 盒路径下该日志可能按 32 位字反序返回，工具会自动识别 `be`/`le32`。
- `FW Download`（opcode `0x11`）：单块 ≤ 4096 B、4 字节对齐，`NUMD`/`off` 以 dword 计；工具发 `trimmed()` = `data[:1024+size]`。
- `FW Commit`（opcode `0x10`）：`cdw10 = (slot & 7) | ((action & 7) << 3)`，slot 3 = SPI Flash，action 1。
- 两份镜像 DWORD32 高 4 位 = 3，即都指向 SPI Flash。

## SMART 持久化与 eMMC 版本约束

- SMART 记录是 eMMC 保留区一个 512 B 块，不在 SPI Flash，**跨刷固件保留**，无 magic/版本/CRC；`0xCD` bit0 选块 1 / 块 3，且被 12 处代码读取，所以「清除用的中间固件必须与最终固件 `0xCD` 同源」。完整机制与刷写流程见 `SMART_BRIDGE_FIRMWARE.md`。
- 固件解析的 EXT_CSD 字段里没有版本寄存器，不存在「必须 5.1」的判断；但主机数据通路只实现了 CMDQ（CMD44/45/46/47），非 CQ 通路是死代码。因此 eMMC 5.0 卡能通过初始化、能 Identify，实际主机 IO 会挂死/超时——这不是版本检查，而是数据通路的实际约束。
- **针对 eMMC 5.0 的固件二进制改造已停止**：该板挂在 USB↔NVMe 桥后面，Admin 命令 / nvme-cli / SMART 透传均不可用，每次重刷要拆板用编程器；两版补丁 v1 无改善、v2 回归（桥枚举期固件死锁、设备完全不识别），且缺少 UART 日志 / PCIe 直连做观测。现改为向厂商索取 non-CQ / eMMC 5.0 兼容 build，或直接换 5.1 颗粒。本仓库的 `FIRMWARE/*.bin` 仅作预置数据文件，工具不现场生成补丁。

## 可信度边界

- 长度、段表、奇偶、XOR 与头字段取值均按文件字节复核，可信。
- 函数级行为来自静态反汇编（SPARC V8），未在真机单步验证；静态结论成立 ≠ 真机可用。
- 刷写中途失败 / 掉电会变砖，只能用 SPI 编程器恢复。
